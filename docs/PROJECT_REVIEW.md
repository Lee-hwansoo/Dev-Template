## 1. 분석 범위와 검증 근거

Git 추적 파일 78개를 대상으로 구조와 의존 관계를 조사했습니다. 중심 경로는
`Makefile → 호스트 감지 → Compose → entrypoint → 셸 함수 → 빌드/의존성 동기화`와
`bake → production builder/runtime → SIF → SLURM`입니다.
GPU·APT·GPG·로깅·메타데이터·IDE·CI 및 관련 문서를 함께 대조했습니다.

판정 기준은 [기여 가이드](../.github/CONTRIBUTING.md)와
[개발 규약](DEVELOPMENT.md)입니다. 공개 API 유지, 영어 프로그램 출력·한국어 문서,
주석 1~2줄, 동작 검증, 불필요한 추상화 배제라는 의도를 우선했습니다.

| 검증 | 결과와 의미 |
| --- | --- |
| `make verify` | 통과. 저장소가 정의한 54개 계약 그룹에 대한 결과이며, 모든 기능 조합의 보장은 아님 |
| 독립 재현 | 추적 파일을 임시 디렉터리에 복사해 설정 전달·판별·정리·TOML 생성·로더·GPU 상태 조회 등을 실행 |
| 삭제 경계 | `docker`, `rm`, `git`, `vcs`를 필요한 경우 기록용 모의 명령으로 대체. 실제 프로젝트·외부 저장소 삭제는 수행하지 않음 |
| Python 예제 | 시스템 Python에는 pytest가 없어 uv 임시 환경의 pytest 8.3.5로 실행. 테스트 2개 통과 |
| 실환경 통합 | 이번 분석에서는 Docker 이미지 재빌드, SIF 변환, 실제 SLURM 작업 제출을 수행하지 않음 |

예제 검증 명령은 다음과 같습니다. 저장소의 의존성 선언과 lockfile은 변경하지 않았습니다.

```bash
uv run --no-project --python /usr/bin/python3 --with 'pytest==8.3.5' \
  python -m pytest -q -p no:cacheprovider src/example
```

아래에서 **실행 확인**은 임시 환경에서 현재 코드를 실행한 결과입니다.
**정적 확인**은 선언·호출·전달 경로를 대조한 결과이며, 실물 이미지나 하드웨어에서의 재현을 뜻하지 않습니다.
README에 기록된 기존 CI·참조 호스트의 실측 결과는 이번 분석의 실행 결과와 구분합니다.

## 3. 우선 수정해야 할 문제

P1은 데이터 손실 가능성 또는 지원하는 기본 워크플로우의 잘못된 실행,
P2는 특정 조건의 기능 누락·부작용·실패 은폐, P3은 문서·주석 정합성 문제입니다.

### R1. P1 — 정리·강제 동기화의 경로 보호가 정규화되지 않음

**위치:** [Makefile](../Makefile) 665~679행,
[setup_sync_deps.sh](../scripts/setup_sync_deps.sh) 26~27·149~167행.

**의도:** 워크스페이스 자체나 허용 범위 밖의 저장소에 파괴적 명령을 실행하지 않는 것.

**실행 확인:** 캐시 경로가 `작업공간/cache/../../작업공간이름`이면 실제로는 작업공간 자체를
가리키지만, 문자열에 `cache`가 있다는 이유로 삭제 분기를 통과합니다. 모의 `rm`에 해당 경로가 전달되고
성공 메시지가 출력됐습니다. 비캐시 경로도 `FORCE=0`이 빈 문자열이 아니므로 통과했습니다.

강제 동기화도 `SYNC_TARGET_DIR=src/thirdparty/../../../outside`를 작업공간 내부 문자열로 판단합니다.
임시 작업공간 밖의 가짜 저장소에서 모의 `git reset --hard HEAD`와 `git clean -ffdx`가 호출됐습니다.
이는 주석의 “정규화된 경로를 비교한다”는 설명과 다릅니다.

**필요한 변경:** 파일시스템 기준으로 경로를 정규화한 뒤 루트·작업공간·허용 경계와 비교합니다.
심볼릭 링크와 `..`를 함께 고려하고, 강제 동기화의 검증은 import/reset보다 먼저 수행합니다.
`FORCE`는 기존 확인 함수와 동일한 참값 규칙을 적용합니다. macOS도 실행하는 경로이므로
GNU 전용 `realpath` 옵션에 의존하지 않는 구현을 선택해야 합니다.

**완료 조건:** 작업공간으로 귀결되는 우회 경로, 외부 경로로 이어지는 링크,
`FORCE=0/false/no`는 파괴적 명령 호출 전에 실패하고, 정상 캐시와 정상 내부 저장소만 처리됩니다.

### R2. P1 — `.env`의 경로 설정이 감지 결과에 덮어써짐

**위치:** [Makefile](../Makefile) 44~46·100~108행,
[check_env.sh](../scripts/check_env.sh) 90~122·278~279행.

**의도:** 프로젝트 기본값과 로컬 설정을 해석해 Docker의 빌드·마운트·실행 경로를 일치시키는 것.

**실행 확인:** 새 캐시를 사용하는 복사본의 `.env`에 `WORKSPACE_PATH=/custom-workspace`와
`DOCKER_DEV_CACHE_DIR=<임시 절대경로>/relocated-cache`를 넣었습니다.
Make에서 최종값을 출력하면 각각 `/workspace`와 `<작업공간>/.docker_cache`가 됩니다.

Make의 파일 변수 export가 감지용 `$(shell ...)`에 전달되지 않는 문제를 ROS 관련 세 변수에만
해결했습니다. 감지기는 경로를 `.env`에서 읽지 않고 기본값을 내보내며, 이후 include가 원래 설정을 덮어씁니다.
특히 캐시는 실제 사용 위치와 `clean-cache`가 삭제하는 설정 위치까지 달라질 수 있습니다.

**필요한 변경:** 감지기가 소비하는 설정 입력을 명시적으로 전달하거나, 공유 설정 해석 경로를 사용합니다.
명령행·환경·`.env`·기본값의 우선순위를 현재 공개 규약에 맞게 고정하고, 같은 입력을 캐시 구분에도 반영합니다.
모든 환경변수를 무차별 export하는 확장은 필요하지 않습니다.

**완료 조건:** 커스텀 작업공간·캐시 경로가 감지 출력, Compose 설정, bake, cleanup에 동일하게 반영되고,
기존 캐시가 있는 상태에서도 입력 변경이 반영됩니다.

### R3. P1 — CMake 자동 판별과 실제 빌드 대상이 다름

**위치:** [util_aliases.sh](../config/util_aliases.sh) 295~310·371~380·574~595행.

**의도:** 실제 사용자 프로젝트의 형태에 따라 빌드와 테스트 러너를 선택하는 것.

**실행 확인:**

- 루트에만 `CMakeLists.txt`가 있으면 `__detect_project_type`은 `PYTHON`을 반환합니다.
  `mbuild`가 지원하는 레이아웃인데도 `mksync`는 빌드를 생략하고 `mtest`는 pytest를 선택합니다.
- `src/thirdparty/lib/CMakeLists.txt`만 있으면 `CPP`를 반환하지만,
  `mbuild`는 루트와 `src/`에 최상위 파일이 없어 실패합니다.

**필요한 변경:** 실제 빌드 진입점을 결정하는 작은 공통 함수를 두고 판별기와 `mbuild`가 함께 사용합니다.
ROS 판별에만 적용한 thirdparty 제외 정책을 CMake 판별에도 일관되게 적용합니다.
중첩된 임의의 패키지를 찾아 자동 빌드하는 새로운 정책은 추가하지 않습니다.

**완료 조건:** 루트 CMake, `src/` CMake, ROS 패키지, 순수 Python, thirdparty만 있는 경우에서
판별 결과·빌드 대상·테스트 러너가 일치합니다.

### R4. P1 — ROS 1 개발 빌드 결과인 `devel/setup.bash`를 로딩하지 않음

**위치:** [util_aliases.sh](../config/util_aliases.sh) 163~173·211~233행,
[init_bash.sh](../config/init_bash.sh) 57~60행,
[entrypoint.sh](../docker/entrypoint.sh) 232~233행.

**의도:** ROS 1은 `catkin_make`, ROS 2는 colcon으로 빌드한 뒤 생성된 환경을 현재 셸과 새 셸에 반영하는 것.

**실행 확인:** `ROS_DISTRO=noetic`인 복사본의 `devel/setup.bash`에 환경변수 설정을 넣었지만
`__smart_source`가 이를 읽지 않았습니다. 실제 ROS가 없는 재현 환경에서는 오류 메시지 뒤에도 함수가 0을
반환했습니다. ROS가 설치된 환경에서는 기본 `/opt/ros/...`만 읽고 사용자 패키지를 놓칠 수 있습니다.

개발용 ROS 1 빌드가 `install` 타깃을 실행하지 않는 것은 의도적입니다.
따라서 해결책은 매번 install을 강제하는 것이 아니라 개발 overlay 선택을 바로잡는 것입니다.

**필요한 변경:** ROS 1 개발 환경은 `devel/setup.bash`, 설치형·production 환경은
`install/setup.bash`라는 규칙을 공통화합니다. 소싱 실패 후 성공 로그를 남기는 경로도 실패를 반환해야 합니다.
production entrypoint는 설치 산출물만 갖는 별도 배포 경계를 유지합니다.

**완료 조건:** ROS 1 패키지 빌드 후 현재 셸과 새 셸에서 패키지를 찾고,
ROS 2·production의 install 로딩은 유지되며, 실패한 setup 스크립트의 종료 상태가 전파됩니다.

### R5. P2 — `mclean`이 ROS 설치 산출물을 남기고 정리 성공을 알림

**위치:** [util_aliases.sh](../config/util_aliases.sh) 600~626행.

**의도:** 기본 정리는 venv를 보존하면서 빌드 산출물을 비우고, `--all`은 venv까지 제거하는 것.

**실행 확인:** 기본 실행은 `install/bin`, `install/lib`만 대상으로 합니다.
`install/pkg/lib/node`, `install/share/x`, `devel/old`가 남아도 성공합니다.
colcon의 패키지별 설치 구조와 ROS 1 개발 산출물이 삭제 범위에서 빠집니다.

**필요한 변경:** 기본 범위를 `build/`, `devel/`, `log/`, 그리고 `.venv`를 제외한 `install/` 내용으로
명시하고 호스트 `clean`과 의미를 맞춥니다. 마운트 지점 자체를 지우려다 발생하는 오류를 통째로 무시하기보다
내용물을 삭제하고 잔여 파일을 확인합니다.

**완료 조건:** isolated/merged install, catkin devel, 숨김 파일을 정리하면서 기본 모드에서 venv를 보존하고,
삭제 권한이 없는 파일이 남으면 실패합니다.

### R6. P2 — `adopt`가 정상적인 설명 문자열로 잘못된 TOML을 생성

**위치:** [Makefile](../Makefile) 292~320행.

**의도:** Python 프로젝트 이름·설명과 Compose 프로젝트 이름을 국소적으로 갱신하는 것.

**실행 확인:** 임시 복사본에서 `make adopt NAME=robot DESC='Robot "A"'`가 성공했지만,
생성된 `src/pyproject.toml`은 TOML 파서에서 실패했습니다.
설명 문자열을 escape 없이 TOML 기본 문자열에 넣으며, 별도로 작은따옴표도 awk 호출의 셸 인용에 영향을 줍니다.

**필요한 변경:** 사용자 입력을 셸 코드에 직접 삽입하지 않고 환경변수 또는 안전한 인자로 전달합니다.
TOML 문자열 escape를 처리한 뒤 임시 결과를 검증하고 게시합니다.
전체 TOML을 재직렬화해 주석과 배치를 바꾸는 방식은 필요하지 않습니다.

**완료 조건:** 작은따옴표·큰따옴표·역슬래시·한글을 포함한 설명이 유효한 TOML로 보존되고,
실패 시 기존 신원 파일이 부분 갱신되지 않습니다.

### R7. P2 — 외부 의존성의 존재 판정이 실행 경로마다 다름

**위치:** [setup_sync_deps.sh](../scripts/setup_sync_deps.sh) 58~137행,
[entrypoint.sh](../docker/entrypoint.sh) 277~290행.

**의도:** 외부 저장소가 있으면 가져오고, 필요한 도구가 없으면 실패하며, 첫 실행에만 자동 동기화하는 것.

**실행 확인:** YAML flow 형식의 유효한 저장소 선언에 전체 커밋 해시를 지정하고,
vcstool이 없는 환경에서 `DEVKIT_REQUIRE_PINNED=1`로 실행했습니다.
핀 검사는 통과하지만 별도의 `url:` 정규식이 선언을 놓쳐 “No external repositories to import.”와 함께 0으로 끝납니다.

첫 실행 검사도 기본 `src/thirdparty/.gitkeep`을 실제 내용으로 계산합니다.
출하된 디렉터리 구조에 검사식을 실행하면 `sync-needed=no`이므로,
사용자가 `.repos`를 채워도 `.gitkeep`이 남아 있는 기본 복사본에서는 자동 동기화를 건너뜁니다.
이 경로는 사용자 설정인 `SYNC_TARGET_DIR`도 사용하지 않습니다.

**필요한 변경:** 이미 수행하는 YAML 해석 결과로 저장소 유무와 핀을 함께 판단합니다.
파서가 없는 경우 내용을 읽지 못한 것을 “빈 목록”으로 처리하지 않습니다.
자동 동기화는 실제 대상 경로를 사용하고 `.gitkeep`을 제외합니다.

**완료 조건:** block/flow YAML, 빈 목록, 누락 도구, `.gitkeep`만 있는 디렉터리,
커스텀 대상 경로에서 import 실행 여부와 종료 상태가 일치합니다.

### R8. P2 — `gpu status` 조회가 호출한 셸의 출력 연결을 변경

**위치:** [util_aliases.sh](../config/util_aliases.sh) 528행,
[setup_gpu.sh](../scripts/setup_gpu.sh) 15~17행,
[util_logging.sh](../scripts/util_logging.sh) 144~156행.

**의도:** GPU 모드 변경은 현재 셸에 반영하되, 상태 조회는 읽기 전용으로 제공하는 것.

**실행 확인:** `gpu`는 항상 스크립트를 source합니다. `NO_COLOR=1`에서 `gpu status`를 실행하면
`devkit_auto_color`의 `exec > >(sed ...)`가 호출한 셸에 적용됩니다.
호출 전후 `/proc/$$/fd/1`의 파이프 식별자가 달라졌고, 이후 출력에도 필터가 남습니다.

**필요한 변경:** `status`처럼 환경 변경이 필요 없는 경로는 서브셸/별도 프로세스에서 실행하거나,
조회 함수 자체에서 색상 출력을 제어합니다. 모드 변경의 source 동작은 유지합니다.

**완료 조건:** 상태 조회 전후 stdout/stderr 연결이 동일하고, 반복 호출에도 필터 프로세스가 누적되지 않으며,
`gpu cpu` 같은 모드 변경은 현재 셸에 반영됩니다.

### R9. P2 — 빌드 후 compile database 통합이 실행되지 않음

**위치:** [util_aliases.sh](../config/util_aliases.sh) 40~43·201행,
[init_bash.sh](../config/init_bash.sh) 105행,
[util_setup_links.sh](../scripts/util_setup_links.sh) 85~112행.

**의도:** 셸 시작은 빠르게 유지하고, 빌드 후에는 IDE가 최신 컴파일 옵션을 읽게 하는 것.

**실행 확인:** 모의 colcon이 `build/pkg/compile_commands.json`을 생성하도록 하고 실제 `cbuild`를 실행했습니다.
빌드는 0으로 끝났지만 `build/compile_commands.json`과 루트 링크는 생성되지 않았습니다.
자동 호출이 모두 `--skip-compile-commands`를 사용하므로 통합 코드는 수동 실행 시에만 작동합니다.
IDE 설정은 통합 파일을 참조합니다.

**필요한 변경:** 빌드 성공 후에만 통합을 수행하고, 셸 시작·venv 생성에서는 생략합니다.
새 캐시나 백그라운드 감시기를 추가할 필요는 없습니다.

**완료 조건:** 최초 다중 패키지 빌드와 재빌드 후 통합 파일이 최신이며,
패키지가 삭제된 경우 오래된 항목도 제거됩니다. 셸 시작은 전체 검색을 하지 않습니다.

### R10. P2 — 공통 로더가 소싱 실패를 성공으로 바꿈

**위치:** [util_paths.sh](../config/util_paths.sh) 46~73행.

**의도:** 공통 스크립트를 성공적으로 한 번만 로딩하고 필요할 때 재로딩하는 것.

**실행 확인:** `return 17`인 임시 라이브러리를 `devkit_require`로 읽으면
호출이 0을 반환하고 loaded 플래그도 `true`로 설정됩니다.
일반 대화형 셸과 오류를 조건식으로 처리하는 호출에서는 부분 초기화를 정상 상태로 기억할 수 있습니다.

**필요한 변경:** source의 종료 상태를 검사하고 성공한 경우에만 loaded 플래그를 기록합니다.
기존 함수의 반환 상태를 전달하면 충분하며, 예외 프레임워크나 새 전역 상태는 필요하지 않습니다.

**완료 조건:** 실패 라이브러리는 실패 상태가 전달되고 다음 호출에서 재시도됩니다.
성공 라이브러리의 1회 로딩과 명시적 재로딩은 유지됩니다.

### R11. P2 — 일부 설정이 Docker 빌드 경계까지 전달되지 않음

**위치:** [apptainer_bake.sh](../scripts/apptainer_bake.sh) 66~94행,
[Dockerfile](../docker/Dockerfile), [Compose 공통 설정](../docker-compose.common.yml),
[util_apt_helper.sh](../scripts/util_apt_helper.sh) 144~154행.

**정적 확인:**

| 설정 | 현재 연결 상태 | 필요한 처리 |
| --- | --- | --- |
| `OPENCV_CUDA` | 개발 컨테이너 런타임에는 전달되지만, bake 인자와 Dockerfile ARG에는 없음. production `mksync`는 기본 `auto`를 읽음 | OpenCV를 빌드하는 단계에 전달하고 `off`의 최종 CMake 인자를 검증 |
| `APT_SNAPSHOT_FALLBACK` | APT helper에 소비 코드와 문서가 있지만 Compose/bake/Dockerfile 전달이 없음 | 광고된 우회 옵션을 관련 빌드 단계까지 연결하거나 지원 범위를 문서에 명시 |

**완료 조건:** 기본값과 다른 값을 넣어 최종 빌더 명령의 인자/환경을 검증합니다.
제거한 미사용 인자를 다른 단계에 형식적으로 추가해 검사를 통과시키는 방식은 피해야 합니다.

## 4. 데드 코드·불필요한 주석·문서 정리

### R12. P3 — 현재 구현과 모순되는 설명부터 정리

| 위치 | 문제 | 최소 수정 |
| --- | --- | --- |
| [DEPLOY.md](DEPLOY.md)의 lockfile 안내 | lockfile 커밋을 요구하는 표와 “DevKit 자체는 lock을 커밋하지 않는다”는 예제가 공존. 실제 `src/uv.lock`은 추적됨 | 오래된 3줄 설명 삭제, 변경 후 lock 갱신 안내로 통일 |
| 같은 문서의 GPG 기본값 | `STRICT_GPG_CHECK=true`와 “기본값은 경고 후 진행”이 모순 | 기본은 불일치 중단이며 명시적 `false`일 때만 경고 후 진행한다고 수정 |
| [DEPENDENCIES.md](DEPENDENCIES.md)와 `setup_gpu.sh` | OpenCV CUDA 활성화에 runtime과 nvcc가 모두 필요하다고 하지만 구현은 nvcc를 기준으로 판단 | GPU 없는 빌더에서도 컴파일하도록 한 현재 의도에 맞춰 설명 수정 |
| `setup_gpu.sh`의 auto 주석 | “Tegra first”지만 NVIDIA를 먼저 검사 | 현재 우선순위를 한 줄로 기술 |
| [util_release_metadata.sh](../scripts/util_release_metadata.sh) 12행 | “metadata must never fail a build”지만 Python 부재·잘못된 epoch·파일 쓰기 실패는 빌드를 중단 | 실패를 숨기지 말고 필수 메타데이터 생성의 실패 규칙을 설명 |
| 같은 파일의 매니페스트 설명 | ROS snapshot 지원을 추가한 코드와 “snapshot mirror가 없다”는 과거 설명이 충돌 | 고정한 입력과 실제 해석 결과를 기록한다는 현재 목적만 남김 |
| [starter test](../src/example/test_starter_node.py) docstring | CMake 프로젝트도 `mtest`가 pytest를 호출한다고 설명하지만 실제로는 ctest 호출 | 실제 테스트 러너 경로에 맞춤 |
| [starter C++](../src/example/starter_node.cpp) | 사용하지 않는 `argc`, `argv`, 구현을 반복하는 주석 | `int main()`으로 단순화하고 C++17 선언을 되풀이하는 설명 축소 |
| [VS Code tasks](../.vscode/tasks.json)의 `.repos only` 작업 | rosdep 옵션 없이 실행하지만 설명은 시스템 의존성 설치까지 주장 | `.repos` 동기화만 수행한다고 수정 |

주석이 길다는 이유만으로 삭제하지 않습니다. 정리 대상은 **현재 사실과 다른 설명, 코드 재진술,
동일한 과거 장애 이야기를 여러 파일에서 반복하는 부분**입니다.
예를 들어 “`--symlink-install`은 dev에서만 사용한다. prod는 `install/`만 복사한다.”는
짧고 필요한 주석이며 유지해야 합니다.

다음은 데드 코드로 분류해서는 안 됩니다.

- `util_logging`의 배너·로그 API와 `util_paths`의 공개 경로/API: 내부 호출이 없어도 제공 API로 선언되어 있습니다.
- deprecated Make 타깃과 `hw_check`: 기존 파생 프로젝트의 호출을 유지하는 호환성 계층입니다.
- `FetchDependencies.cmake` 예시, `.repos` 예시, overlay의 ignore 파일: 템플릿 확장 지점입니다.
- APT의 `# runtime`, `# dev`, `# ros1` 등: 파서가 소비하는 메타데이터입니다.
- production entrypoint의 별도 경로 정의: 배포 이미지에 개발용 config/scripts가 없다는 경계 때문에 필요합니다.
- compile database 통합 코드: 죽은 구현이 아니라 자동 호출 연결이 빠진 기능이므로 R9처럼 연결을 복구해야 합니다.

## 6. 수정 순서와 완료 판정

1. **R1~R2:** 삭제 경계와 설정 전달을 먼저 복구합니다. 데이터와 실행 경로를 잘못 선택하는 문제입니다.
2. **R3~R5:** 프로젝트 판별·ROS overlay·정리의 지원 레이아웃을 맞춥니다.
3. **R6~R11:** 문자열 입력, 의존성 유무, 조회 부작용, IDE 생성물, 로더 실패, 빌드 인자 전달을 수정합니다.
4. **R12:** 확정된 동작에 맞춰 주석·문서·도움말을 정리하고 미사용 내용을 제거합니다.

각 변경은 기존 `make verify` 통과 외에 위 항목의 **완료 조건을 검증하는 동작 테스트**가 필요합니다.
프로젝트의 기여 규약에 따라 새 회귀 검사는 해당 수정만 되돌렸을 때 실패하는지도 확인해야 합니다.
이 보고서 작성 단계에서는 구현 수정이나 그 수정에 대한 뮤테이션 검증을 수행하지 않았습니다.

전체 개선 완료는 “계약 그룹 수가 늘었다”가 아니라, 같은 입력이 호스트·빌더·실행 환경에서 같은 효과를 내고,
실패는 실패로 반환되며, 정리 명령이 허용한 산출물만 삭제하는 것으로 판정해야 합니다.
